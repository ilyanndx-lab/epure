# `pip freeze` du site-packages Python 3.12 embeddable qui a produit et vérifié le
# paquet du 2026-09-24 (136,3 Mio zippé, 388,6 Mo décompressé, 61 distributions).
# Généré, pas écrit à la main : ne pas éditer une ligne isolément. La procédure
# est celle que l'en-tête précédent décrivait — construire avec
# `--sans-contraintes`, puis relire `python.gel` du `PAQUET.json` produit.
# `test_paquet.py::ContraintesCouvrentExigencesTest` refuse désormais qu'une
# exigence installée manque ici, ou y figure à une autre version.
#
# ── Régénéré le 2026-09-24 : fastapi dégelé, et un mois de dérive rattrapé ────
#
# Déclencheur : `fastapi` 0.136.3 → 0.141.1 et `starlette` 1.2.0 → 1.7.0
# (le démontage de routes à chaud, qui gelait fastapi, a disparu — cf.
# `backend/requirements.txt`). Ce qui a bougé d'autre n'en est PAS l'effet :
# mesuré par `pip install --dry-run` des exigences du jour sous l'ancien gel
# privé de ses deux lignes fastapi/starlette, la résolution passe avec
# l'ancien `anyio` 4.14.2 et l'ancien `pydantic` 2.13.4. Les montées
# transitives ci-dessous sont un mois de publications PyPI, rien d'autre.
#
# ARRIVÉS : `readability-lxml` (dépendance DIRECTE ajoutée sans régénérer ce
# fichier — elle se résolvait librement, ce qui a fait écrire le test
# ci-dessus) et sa grappe `lxml-html-clean`, `cssselect`, `chardet`.
#
# REVENU : `setuptools` (même version, 84.0.0). Le paquet du jour en était
# privé avant correction : `get-pip.py` a cessé de l'amener, et c'est
# `faire_paquet.preparer_python` qui l'installe nommément désormais, avec un
# contrôle bloquant en fin de construction.
#
# DÉRIVE (transitifs) : `anyio` 4.14.2→4.15.1, `ctranslate2` 4.8.1→4.8.2,
# `filelock` 3.32.4→4.0.3, `fsspec` 2026.7.0→2026.9.0, `huggingface_hub`
# 1.28.0→1.33.0, `idna` 3.19→3.20, `jiter` 0.16.0→0.17.0, `lxml` 6.1.2→6.1.3,
# `protobuf` 7.36.0→7.36.2, `pydantic` 2.13.4→2.13.5, `pydantic_core`
# 2.46.4→2.46.5, `tokenizers` 0.23.1→0.23.2, `tqdm` 4.70.0→4.70.1, `tzdata`
# 2026.3→2026.4.
#
# `filelock` 4 est une version MAJEURE : elle a été exercée dans le paquet
# installé, sur le chemin réel qui la traverse — premier usage de la
# transcription (`core.voice.WhisperEngine`, modèle `tiny`, cache HF vide) :
# `huggingface_hub` y prend 4 verrous `WeakFileLock`, le modèle se télécharge,
# `ctranslate2` le charge, la transcription tourne. Pas d'épinglage `<4`.
#
# PARTIS : aucun.
#
# ── La leçon du 2026-08-26, qui vaut toujours ────────────────────────────────
#
# Un fichier de contraintes périmé est inoffensif jusqu'au jour où il épingle,
# à une autre valeur, quelque chose qui vient de devenir direct : ce fichier
# portait `onnxruntime==1.28.0` en transitif quand `requirements.txt` l'a
# déclaré `==1.26.0`, et `pip install -c` a échoué sur la résolution avant la
# première wheel. Le test ci-dessus vérifie aussi cette concordance.
#
# Aucun `torch`, `sentence-transformers`, `scikit-learn`, `scipy` ni
# `transformers` : ils n'ont jamais été dans un paquet (ils étaient reportés « au
# premier usage »), et ils ne partent toujours pas : `transformers`, revenu dans
# `requirements.txt` pour `core/hmer.py`, est dans `HORS_PAQUET_PIP`. C'est
# `onnxruntime` qui porte l'embedding, et il pèse **12,9 Mo dans l'archive**
# (38,4 Mo décompressés) — mesuré sur l'archive du 2026-09-24 elle-même
# (construite AVEC ce fichier), dossier + `.dist-info`, Mo décimaux. Inchangé
# depuis la mesure du 2026-08-26 : même version, 1.26.0.
#
# `tokenizers` est encore là, et ce n'est PAS pour l'embedding : `faster-whisper`
# le déclare. Le tokeniseur d'Épure est du Python pur (`core/wordpiece.py`),
# précisément parce que le `.pyd` de `tokenizers` n'est pas signé — la catégorie
# de binaire que Smart App Control bloque sur la machine ARM64 du destinataire.
# Sur un paquet `--arch arm64`, la voix est retirée (`HORS_PAQUET_PIP_ARM64`) et
# `tokenizers` disparaît donc avec elle : **68,8 Mo d'archive** en tout
# (178,1 Mo décompressés), dont 2,7 Mo pour `tokenizers` et 66,1 Mo pour `av`,
# `av.libs`, `ctranslate2`, `piper`, `faster-whisper`, `hf-xet`,
# `huggingface-hub` — mesuré le 2026-09-24 sur l'archive x64 (dossiers +
# `.dist-info`, Mo décimaux ; 68,6 Mo annoncés au 2026-08-26). Un ordre de grandeur pour l'ARM64,
# pas une mesure de l'ARM64.
#
# ── Pourquoi ce fichier existe ────────────────────────────────────────────────
#
# `backend/requirements.txt` épingle les paquets DIRECTS, mais son résolveur reste
# libre sur l'arbre transitif : mesuré, `google-generativeai==0.8.6` rétrograde
# `protobuf` selon ce qui est publié sur PyPI au moment du build. Ce fichier fige
# l'arbre entier. Il est utilisé par défaut ; `--sans-contraintes` l'ignore (pour
# régénérer après un changement de `requirements.txt`, exactement le cas de ce
# lot-ci), `--contraintes` en pointe un autre.
#
# ⚠️ Il décrit un environnement **x64**. Une cible `win_arm64` n'a aucune raison
# de résoudre les mêmes wheels : pour cette architecture, construire d'abord avec
# `--sans-contraintes` et en générer un fichier séparé si la reproductibilité
# devient nécessaire là aussi.
#
# ⚠️ `setuptools` y est, `pip` **non**, et ce n'est pas une purge : `pip freeze`
# s'omet lui-même. `pip` EST bien dans le paquet (`PURGE_SITE_PACKAGES` est vide
# depuis le 2026-08-23, vérifié dans l'archive : `python/Lib/site-packages/pip`) —
# un paquet sans `pip` est un paquet qu'on ne peut pas réparer, et
# `core/embedding_install.py` recommande nommément `pip install -r
# requirements.txt` quand `onnxruntime` manque. Ne pas lire l'absence de sa ligne
# ci-dessous comme son absence du paquet : ce fichier est un gel de dépendances,
# pas un inventaire de l'archive.
#
# La leçon que ce fichier porte depuis 2026-08-13, et qui n'a pas changé : une
# grappe transitive ne se lit pas comme du poids mort du seul fait qu'elle
# disparaît avec son porteur. `watchfiles` et `httptools` l'étaient ;
# `websockets`, partie dans le même lot, ne l'était pas — et son départ a coûté
# tout `/ws/*` chez un destinataire. Rien ne les distinguait.
